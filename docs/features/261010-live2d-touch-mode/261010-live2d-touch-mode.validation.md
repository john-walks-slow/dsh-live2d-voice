## 二、HUD 拆层的等价性取证（auto-human 的 4 项核对）

1. **胶囊盒子逐像素等价**：把新增的触摸模式按钮隐藏、把全屏按钮临时挪回胶囊原位后，`.lv-capsule` 的 rect 与改动前 `.lv-hud` **完全相同**（`316.5, 620, 267×48`）；胶囊区域像素差异 **23/16740 = 0.14%**，最大通道差 19（抗锯齿级）。脚本 `capsule-baseline.mjs`（改前基线）、`capsule-equiv.mjs`（改后等价性）。
2. **绝对定位后代盘点**：`.lv-hud` 子树里唯一的绝对定位元素是 `.lv-pop`，其 containing block 从 `.lv-hud` 变成 `.lv-capsule`（同一个盒子），实测计算值 `bottom = padding-box(46px) + 12px`、右对齐一致 ✓；`.lv-btn` 自身 `position:relative`，所以 `.lv-btn.lv-mic-live::after` 的脉冲光环仍锚在按钮上。其余（`.lv-micbar` / `.lv-input` / `.lv-toast` / `.lv-center` / `.lv-calib-*` / `.lv-root:fullscreen`）都不是 `.lv-hud` 后代，锚点不受影响。
3. **几何读取面**：e2e 里没有任何一处读 `.lv-hud` 的 rect/offset；只有 `display:none` 隐藏（`verify-fullscreen-usable`、`verify-keyboard-squish` 做像素测量时用——层化后隐藏整层会连带隐藏角落簇，模型 bbox 更干净）、存在性布尔（`verify-live`/`verify-standalone*`）与后代点击选择器（`.lv-hud button[title*=…]`、`.lv-hud .lv-mic`、`.lv-hud [title*="快捷调整"]`）——**0 处 e2e 改动**。
4. **淡出与可达性**：`layer-checks.mjs` 4/4 —— root layer `pointer-events:none`、`.lv-pop` 锚点、角落簇淡出 0.45、`focus-within` 提亮 ✓（`.lv-hud.lv-mic-live.lv-faded` 例外只抬胶囊）。

## 三、视线方向度量与阈值标定（T8）

- 方法：手指固定在画面左 12% / 右 88% 处按住，各等视线 settle 900ms 后截帧；用 PIL（复用 `verify-fullscreen-usable` 的角落采样背景法）在**上半屏**取非背景像素的**水平质心**（按屏宽归一）。
- 实测（haru / 900×700 / 第一人称）：`left=0.3575`、`right=0.6466` → **位移 0.2891**；同一位置连拍两帧漂移 **0.0002**。
- 阈值取 **0.05**（噪声的 250 倍、信号的 1/6），方向断言（右 > 左）同时成立。数值写进套件注释。

## 四、未覆盖 / 说明

- **三个 GUI 全屏套件未通过（环境所限，非本改动回归）**：`verify-fullscreen-usable` / `verify-fullscreen-keyboard` / `verify-keyboard-squish` 都需要实例里存在**真实 chat 会话**（点 `[role="treeitem"].sessionRow` → 会话页签 "Live2D"），最小 e2e 实例只有空会话，故在 `waitForSelector('.lv-root .lv-stage canvas')` 超时失败——失败发生在与 HUD 交互之前，与本改动无关。等价覆盖由 `verify-standalone-fullscreen`（走 standalone 入口的角落全屏按钮 + 原生全屏 + 几何）与 `verify-touch-mode` T5a/T5b 承担。
- **玩家化身**没有独立的手势/空闲调度；**鼠标**不做 flick；**参数面板/表情选择器**不在本轮（计划 §二非目标）。
- 主观手感（跟手程度、滑动阈值是否顺手、角落按钮位置）请用户真机确认，见 §五。

## 五、真机验收清单（触摸模式）

> 归因基线（线上跑的就是被检过的那一版、sha256 与配置写入的如实记录）见 `261010-live2d-touch-mode.baseline.md`。

每条都写了**期望现象**，摸的时候对着看；哪条不符就把编号告诉我。

| # | 操作 | 期望现象（不符即为问题） |
|---|---|---|
| 1 | 打开触摸模式：工具条上的手指按钮，或 ⚙ 系统设置卡里的「触摸模式 (touchMode)」开关 | 按钮点亮、设置卡下拉变成「开启」；**首次**开启时底部弹出一行提示（"角色跟着你的手指看…"）约几秒后消失；刷新页面后开关**仍是开启**（这是 host 侧持久化生效的判据） |
| 2 | 手指按住屏幕任意位置并缓慢移动 | 角色**头与眼同时**转向手指方向，跟手无明显延迟（<0.2s 的滞后可接受）；手指移到最左/最右时转向角度接近上限但不"翻白眼"；**不要**出现模型整体平移 |
| 3 | 抬起手指 | 视线在**约 0.5 秒内平滑**回到摄像头视线（开着眼动追踪）或回到正视（没开）；全程**无跳变**、无突然复位；不会卡在手指最后的位置 |
| 4 | 单指拖动；然后两根手指捏合/拖动 | 单指**不再**平移模型（只有视线跟手）；双指能平移与缩放；双击仍复位视图 |
| 5 | 轻触角色的头/身体；再快速左右、上下划动 | 轻触触发它自带的 `Tap` 动作（一次轻触一个动作，不乱播）；滑动触发 `Flick` 系列动作（左右能分别触发左右；上下若模型没有对应动作会退化成它自带的另一个手势动作）；**连续快速滑动不会打满动作队列**（约 0.4 秒内只算一次） |
| 6 | 桌面鼠标（不用按键）在画面里移动；再按住拖动 | 鼠标移到哪角色看哪（与开摄像头时同一套幅度）；按住拖动**仍是平移**、滚轮缩放；鼠标快速甩动**不会**触发手势动作（鼠标没有 flick 语义） |
| 7 | 点右上角簇的全屏按钮；退出全屏 | 按钮在右上角、不被系统状态栏/下拉手势挡住；进入沉浸全屏后画面铺满、比例不变形；再点能退出（不留死路） |
| 8 | 关掉触摸模式后重复第 2 条 | 单指拖动恢复为**平移**模型、角色不再跟手指、也不写跟手向量；重开则恢复第 2 条行为 |

**刻意行为（不是 bug，不用报）**：
- 语音对话中角色正在播剧本动作（LLM 打的动作标签）时，轻触/滑动会被**静默忽略**（该动作播完再划即可）——手势与点击同为 NORMAL 优先级，不抢剧本动作。
- 连续快划有 400ms 冷却，第二次滑动在冷却窗口内不生效（防刷屏）。
- 触摸模式开启时单指不平移是设计（平移交给双指）——手感不习惯就先关掉开关，它会记住。

| 9 | 触摸模式开、选 `official/izumi`；连续快速右划 10 次（每次都等前一次动作结束再划，然后再试"不等就划"） | 等动作结束再划：**10/10 都应触发**；不等就划（动作还在播时立刻再划）：**允许偶发不响应**（这是刻意设计：NORMAL 手势撞上正在播的动作会被静默拒绝） | **判定**：等动作结束再划仍有 ≥1 次无响应 = FAIL（说明手势链路有真问题）；"不等就划"偶发无响应**不算 FAIL**，但请记录大概几次、以及是否觉得手感受影响（e2e 侧同样现象见 §十 未结项） |

**已知边界（不算验收项）**：玩家化身（第三人称/视频通话里你的小窗）没有独立的手势/空闲调度；鼠标没有 flick；表情/参数面板不在本次范围。

## 八、手感四项判定线（真机照做，缺一条即为不可判）

| # | 前置条件 | 操作步骤 | 期望现象 | 判定线（不满足 = FAIL） |
|---|---|---|---|---|
| 2 | 触摸模式开；第一人称单模型；模型库选中 `haru`（或任意有时间轴的模型）；无语音播放 | ① 手指按在画面左侧 1/4 处保持 1 秒；② 保持按压，用 **≥1 秒**的时间匀速横向划到右侧 1/4（约 400px）；③ 在右侧保持 2 秒 | 头部与眼球**连续**跟随手指方向，中途不回弹、不跳格；到两侧时接近该模型角度上限（不是只动一点点，也不"翻白眼"）；**模型整体位置不动** | **主观**：肉眼能看出"头/眼明显落后于手指"或移动中途卡顿/跳变即 FAIL。**可选客观**：60fps 录屏，手指停止移动后头部到达该方向最大偏转的时间 **> 300ms** 即 FAIL（低于此不可靠，不设硬指标）；两侧端点的水平质心差应 ≥ 0.05 屏宽（e2e T8a 用的同一口径） |
| 3 | 同第 2 条；若开了摄像头视线追踪更好（能看交接） | ① 按住画面右侧 1/4 保持 1 秒让视线偏到右侧；② 抬手，目不转睛看 1 秒 | 视线在**约 0.5 秒**内平滑滑回摄像头视线（未开则回正视），全程无跳变、无突然复位、不会卡在右侧 | **主观**：出现"啪"一下的瞬移、或抬手后 1 秒仍停在右侧即 FAIL。**可选客观**：抬手后每 180ms 截帧算头素质心（e2e T8d 同一口径），单帧位移 **> 0.18 屏宽** 即判跳变 FAIL；末帧相对抬手帧的位移应 ≥ 0.05 |
| 5 | 触摸模式开；选**带 Tap 与 Flick 的模型** `official/izumi`（只有 Flick 的换 `chitose`，只有 Shake 的换 `oc/luna`） | ① 轻触头部一次；② 等动作播完，快速右划一次；③ 等动作播完，快速左划一次；④ 接着 0.5 秒内连续快划 5 次 | ① 触发一个自带动作（头/身体动一下），**不是**连播多个；② 右划触发右向手势动作；③ 左划触发左向；④ 连续快划**不会**连播 5 个（约 0.4 秒窗口内只认一次） | **判定**：轻触一次播多个动作 = FAIL；左右划方向反了 = FAIL；连续 5 次快划触发 ≥ 3 个动作 = FAIL（`dataset.lvGesture` 可对照，见 §七）。模型没有对应方向组时退化成它自带的另一个手势动作**不算 FAIL**（设计如此） |

即：**注册本身很快（≤160ms）**；失败不是"等待窗口太短"，而是这一次滑动被框架静默拒绝、

每次尝试都必须有新的接受计数，否则不算成功。

### 第二轮交叉核查：`getCurrentPriority()` 恒为 0 的根因（已定论）

我一度写下"本构建 MotionManager 起播不带优先级，所以拿不到精确信号"。审阅者指出这与上一轮的错误同型号（把"我查的那条路不通"当成"没有这条路"）。独立源码判定（`docs/issues/261010-motion-priority-signal/`）结论：

- **不是**调用点传错优先级：`Live2DModel.motion(group, index, priority)` → `MotionManager.startMotion(group, index, priority)`，我们的 `handleTap`/`handleSwipe`/`playMotion` 都按第三参正确传值；
- `queueManager` 是 `CubismMotionQueueManager`，它的 `startMotion(motion, autoDelete, userTimeSeconds)` 第三参是时间、**不维护** priority——所以 `getCurrentPriority()` 恒为 0 属"查错对象"，不是"库不支持"；
- 优先级实际在 `MotionManager.state`（`currentPriority` / `reservePriority`，`MotionState.reserve/start` 用它拒绝新动作）；

**修法落地**：`dataset.lvMotionBusy = max(state.currentPriority, state.reservePriority) >= 2`，精确判断"NORMAL 会不会被拒"。拿到它之后重试被删除：助手改为"等空闲 → 单次滑动"，实测 `1 次 ×7` 全绿（`38/38`）。

**这一轮的教训**（与上一轮同形，值得并列记下）：**"我查的那个接口没用" ≠ "这条路不存在"**；定位不到精确信号时，先穷举"接口/对象/时机"三种可能，再决定是否写成"需要上游支持"。

**第三轮跟进（门槛项，均已落地）**：

- **内部状态类断言必须带正向对照**。`lvMotionBusy` 来自内部 `state.currentPriority/reservePriority`，若读错对象/字段名对不上，
  `max(...) >= 2` 恒为假 → 等归零瞬间返回 → **整条链照样全绿**。因此新增 **T18 正向对照**：动作播放期间必须观测到
  `lvMotionBusy === "1"`（至少一次采样），播完后必须回到 `"0"`，观测不到即红。实测：
  `武装=Right:FlickRight 采样前若干=1 见到1=true 之后回0=true`。这条把"源码级结论"变成了"经验证据"。
- **等待超时 = 失败**（**源码核对，未实跑验证（证据级别：静态）**）：`swipeOnce` 在 `waitMotionIdle()` 超时（4s）时返回
  `ok=false, reason='idle-timeout'`，不再继续往下走。**这条只是代码事实：我没有跑过"超时→红"的红路用例**
  （要造"队列 4s 不空闲"需要比现有模型更长的动作或人为阻塞，未做）。不要把它当观测结论。
- **权威信号是返回值，不是采样**：`model.motion(...)` 声明为 `Promise<boolean>`（`types/index.d.ts:1771`），
  产品代码在 `handleSwipe` 里用它做闸门。**"e2e 的判定因此等价于返回值判定"这个说法依赖一个前提，已单独 grep 确认**：
  `dataset.lvGesture` 全仓**唯一写入点**是 `model.ts:673`（该闸门内的成功分支），`lvGestureSeq` 的写入点只有
  `model.ts:677`（同一分支）与 `:1002`（destroy 时删除），**没有任何读方**。所以在"唯一写入点"这个前提下，
  测试观察到的 DOM 契约只可能来自那次调用的成功返回——这是**源码级证据链**，不是话术；
  但链路本身仍是静态核对（未做运行时注入反证）。`lvMotionBusy` 只是**发滑动前的提示**，不承担判定职责。
  完整理由：`docs/issues/261010-motion-priority-signal/`。
- **旧信号删干净**：`src/client/model.ts` 里已无 `getCurrentPriority()` / `queueManager` 判忙路径（仅注释里留了"为什么不用它"）。

复跑：`verify-touch-mode 39/39`（分布 `1 次 ×8`）、`verify-tap 11/11`。

**门槛 3 的红路已补（升级为已验证）**：把 `handleSwipe` 成功分支里的 DOM 契约写入临时注掉（`if (false) container.dataset.lvGesture = value;`），
重跑同一套件 → **32/39，手势相关 7 条全部转红**（T4a/T4b/T4c/T5/T6a/T6b/T18 都读不到契约值），恢复后 39/39。
这证明"e2e 观察的契约确实只由那次成功返回写入"——不再只是静态推理。红路注入是**临时**的，未提交（`src/client/model.ts` 已从备份恢复并重跑绿灯）。

（扫描里 t=800/1000ms 各 3/3 被拒）。这不是"可能更差"，而是已经量化。

### 机制判定：死区 = **上一个动作自己的播放期**（(i) 成立，(ii) 排除）

用"片长不同的动作"做自然实验（同一组 t，只换武装动作）：

| 武装动作 | 片长（`Meta.Duration`） | t=2200ms | t=2600ms | t=3000ms |
| --- | --- | --- | --- | --- |
| 左划 → `FlickLeft` | **1.90s** | ACCEPT ×2 (busy=0) | ACCEPT ×2 | ACCEPT ×2 |
| 下划 → `Shake` | **4.13s** | **REFUSE ×2 (busy=1)** | REFUSE ×2 | REFUSE ×2 |

**同一组 t、不同片长 → 结果相反**：死区随片长整体平移 ⇒ **是动作的播放状态在挡（(i)），不是动作结束后另起算的冷却（(ii)）**。
因此"手势动作自己的播放期在挡自己"这一条**成立**（也正是最便宜、语义零变化的方向）。

izumi 的手势片长（`Meta.Duration`，秒）：`FlickLeft` **1.90**、`FlickRight` **2.57 / 2.63**、`Shake` **4.13**；
所以先前测到的"≈1.6–1.8s"其实是"FlickLeft 1.9s ± headless 帧量化（±0.5s）"，**死区应表述为"≈上一个手势动作的片长（izumi 1.9–4.1s，随模型而异）"**。

**补测：把边界跨过去才叫观测到"门开了"**（Shake 片长 4.13s，之前只测到 3.0s，全在窗口内）：

```
武装 = 下划（Shake 4.13s）：t=4500ms ACCEPT ×2、5000ms ACCEPT ×2、6000ms ACCEPT ×2（busy 全为 0）
武装 = 左划（FlickLeft 1.90s）：t=2200ms ACCEPT ×2（> 片长）   ← 已跨过边界
```

⇒ 两条臂都**观测到了释放**，且释放点贴合各自片长（1.9s / 4.13s）→ **死区 = 上一个动作的播放期**在两条臂上都是实测。

**排除 confound（同一实验的对照项）**：
- **优先级**：所有手势都走同一个 `handleSwipe`、同一个 `priorityValue("normal")`（`src/client/model.ts:683`）；
  剧本动作才用 `force`（`:936`）→ Flick 与 Shake **不是**不同代码路径，也不是 FORCE。
- **Loop 标志**：izumi 的 `FlickLeft`/`FlickRight`/`Shake`/`Tap` 的 `Meta.Loop` **全部为 `True`**（相同），
  但实测两者都在 `Meta.Duration` 处释放 → Loop 不构成差异，gate 是**播放时长**。

**gate 的位置（实现前必须钉死）**：拒绝发生在**库内部**的 `MotionManager.startMotion` → `MotionState.reserve/start`
（`dist/cubism4.js`），不是我们的代码。但库**公开**了 `stopAllMotions()`：它清空队列**并调用 `this.state.reset()`**
（`dist/cubism4.js:9203`，`MotionState.reset` 在 `:8366`）→ 之后 `startMotion` 会被接受。
**结论：抢占在公开 API 可达**（`stopAllMotions()` + 起播新动作；新动作自带 fade-in，避免硬切）。

**"拒绝"= 丢弃，不是排队；"接受"= 返回值 true 且真的在播**（`gesture-queue-check.mjs`，t = 200/600/1000/1400/1800/2100ms，各 2 次）：

```
每个 t 上第二发的结果：返回值(seq 前进) = N ×2；3 秒内"迟到出现" = 0 次
判读：没有任何"迟到出现" ⇒ 被拒 = 丢弃，不是排队；返回 true 的都会进入播放态 ⇒ 返回值 = 真的起播
```

（返回值即 `model.motion(...)` 的 `Promise<boolean>`；`lvGestureSeq` 只在它 true 时写入。因此本报告里的
"ACCEPT/REFUSE" 与"返回值 true/false"是同一件事，而"排队"这一替代解释被 3 秒观察窗排除。）

**抢占方案的四个前置钉子（源码冷读 + 实测，报告：`docs/issues/261010-motion-preempt/261010-motion-preempt.troubleshoot.md`）**：

| 钉子 | 结论 | 证据 |
| --- | --- | --- |
| ① "拒绝"是丢弃还是排队 | **丢弃**（同优先级直接 `false`），返回值 true = 真的起播 | 库 `MotionState.reserve`：`s <= currentPriority` 即 `false`（`dist/cubism4.js:8259-8267`）；实测 3s 观察窗内**零迟到出现**（`gesture-queue-check.mjs`） |
| ② `stopAllMotions()` 副作用面 | **只清 motion queue / state / audio**；**不动** expression / eyeBlink / breath / physics / pose | `dist/cubism4.js:9203-9207`；`MotionState.reset()` 仅清 current/reserved 字段 |
| ③ 抢占后 idle 是否自恢复 | **会**：`update()` 在队列 finished 后 `complete()` + `shouldRequestIdleMotion()` → 重新请求 `groups.idle`；`state.reset()` 不清 `groups.idle` | `dist/cubism4.js:9214-9227`（注意：库侧没有 `idleInterval` 字段，那是我们自己的配置） |
| ④ 能否做到"极短淡出/平滑抢占" | **公开 stop+start 路径做不到淡出**（旧 entry 被直接丢弃）；但**新动作自带 fade-in**（默认 `motionFadingDuration = 500ms`，动作自身 `FadeInTime` 优先） | `config.motionFadingDuration: 500`；`createMotion` 设 `setFadeInTime`；`_startMotion` 先 `queueManager.stopAllMotions()` |
| ⑤ `Meta.Loop=true` 时 `onFinish` 是否触发 | **不触发**（循环动作重置 startTime，不 set finished） | `CubismMotion` `:3680-3692`；且库的公开 `startMotion` 解构了 `onFinish` 却没传给 `_startMotion`（`:9142`） |

**抢占的混合语义（最后一道钉，headless 实测）**：新动作从上一次动作的**末帧姿态淡入**，**不会在 f=0 跳变到基础姿态**。
`motion-preempt-mix.mjs`（临时探针构建逐帧发布的姿态参数，用后已回滚）在被抢占动作播放期间建立"基准帧间角度增量"分布，
再比较"抢占前最后一帧 → 抢占后第一个变化帧"的增量：

```
基准（播放中每帧角度最大增量）：中位 4.1–4.2°，最大 7.2–8.4°
跨越抢占的第一个变化帧：        0.78–3.10°（**小于**基准，因为新动作 fade-in 从权重 0 起步）
嘴部：基准最大 0.87–0.95 → 跨越 0.04–0.11
```

⇒ **抢占不会产生姿态 snap**，因此**不需要**"只允许同类/同向手势被抢占"那套备选实现；
过渡只有"新动作自带 ~500ms fade-in"这一层（与原设计一致）。
（探针细节：先在 `src/client/model.ts` 注入临时 `__lvProbe` + 逐帧 `dataset.lvPoseProbe`，用 esbuild **只构建 standalone**、
不碰 `lib/index.js`；测完已把 `model.ts` 回滚到提交版本，探针构建也被已提交产物覆盖。）

**对实现设计的两条硬约束**：
1. **状态标记绝不能靠 `onFinish` 清除**（⑤：循环动作永不触发，且公开路径根本没注册回调）→ 改为"**所有起播路径（手势 / 剧本 / 待机）走同一个入口写标记，后起的覆盖先前的**"，陈旧标记在结构上不可能存在；
2. **不能把"极短淡出"写成兜底**（④：做不到）→ 抢占的过渡只能是"新动作自带的 fade-in（~500ms）"；若真机逐帧看出现 snap，需要回来改需求（例如只允许同类/同向手势被抢占），而不是硬加淡出。

**修法含义**：既然 gate 是"上一个动作在播"，最小改动是让**手势能抢占上一次手势触发的动作**（不改动模型自带/剧本动作的语义），
即"动作缘起分支抢占"；"把动作改短"要靠产品侧提前停止/淡出该动作，本质上与抢占是同一条路。

### 缺陷级发现：主手势存在 ≈1.6–1.8s 的输入静默黑洞（待裁决方案，本轮不改行为）

按预先约定的触发条件（"若扫描出的死区达到 ~1s 量级，就不是待定项而是缺陷"），本轮扫描结论 **1.6–1.8s ≥ 1s → 成立**：

- **现象**：手势动作（Flick/Shake）起播后约 **1.6–1.8s** 内，新的滑动**全部被静默丢弃**（无排队、无提示、无任何用户可见反馈）；
- **机制**：手势以 **NORMAL** 优先级起播，而框架的规则是"优先级 ≤ 当前预留优先级"的动作被拒——播放中的 NORMAL 动作会挡住新的 NORMAL 手势
  （IDLE 优先级不算忙，这一点已由 `lvMotionBusy` 只在 NORMAL/FORCE 时为 `"1"` 证实）；
- **影响**：人类快速连划（0.5–1s 间隔）基本必然丢第二次；用户可能误以为功能坏了。

**候选方案（不在本轮实施，等裁决）**：
1. **排队**：被拒的手势缓存一次，待当前动作结束后立即起播（延迟可见但输入不丢）；
2. **抢占**：手势改用 FORCE 优先级打断当前动作（语义变化：会打断正在播的动作，含模型自带的）；
3. **缩短死区**：手势使用更短的动作（或加一个短确认动作），把死区压到接近冷却窗口；
4. **反馈**：至少让"被拒"可见（例如轻微提示），避免用户以为坏了——**这条与是否排队独立**，成本最低。

**未决问题**：拒绝目前是**静默**的（动作没起播、界面无提示）。判断"要不要排队/抢占"的真正依据是"用户会不会以为坏了"，
而不是采纳率本身；真机手感（§十三 第 12b 项）与上面的候选方案一并裁决。

## 十四、抢占方案的验收口径与已钉前置

> 本节是**实现前**钉下的口径（保持不变）。实现记录、跑出来的证据与两处"为错误机制而绿"的坑见 **§十五**。

### 三态状态机（真实运行态回答"在不在播"，来源标记回答"谁起的"）

| 运行态：`max(state.currentPriority, state.reservePriority)` | 来源标记（单一入口写，后起覆盖先起） | 滑动到达时的动作 |
| --- | --- | --- |
| `< 2`（空闲，**含只有 IDLE 在播**） | 不参与判定 | **正常起播**（框架本就接受，无需抢占） |
| `>= 2` 且标记 = `gesture` | `gesture` | **抢占**：`stopAllMotions()` → 起播本次手势（`preemptGesture++`） |
| `>= 2` 且标记 = `script` | `script` | **拒绝**（保持）+ HUD 手指按钮闪 ≤200ms（`rejectScript++`） |

标记**只在 `busy === true` 时被查询**，因此"剧本/idle 播完后标记仍旧"不会造成永久拒绝（那时走空闲行）；
`onFinish` 不可用于清标记（循环动作不触发，且公开 `startMotion` 根本没把 `onFinish` 传给 `_startMotion`，`:9142`）。

**剧本动作的真实优先级（file:line，替代"FORCE 代餐"的断言）**：`view.tsx:965` 的 `onMotion`（LLM motion tag 的落点）调用
`target.playMotion(def)` → `model.ts:936` 用 `priorityValue(priority ?? "force")` → `model.ts:916-924` 映射 `force → 3`。
即**剧本路径传的就是 FORCE(3)**；因此"注入一次 FORCE 动作"与真实剧本路径在**优先级语境**上等价
（且都是同一次 `model.motion(group, index, 3)` 调用，差别只有我们 wrapper 的 try/catch 与日志）。
HUD 手动选动作（`view.tsx:1909`）同样不传优先级 → 也是 FORCE；待机调度（`view.tsx:785`）显式传 `"idle"`(1)。

**规则引用（不靠口述）**：IDLE=1 / NORMAL=2 / FORCE=3；`MotionState.reserve` 中
`s < 3` 时 `if (s <= this.currentPriority) return false`（**`dist/cubism4.js:8259-8267`**）——
即 IDLE 被 NORMAL 抢占是框架语义，NORMAL 撞 NORMAL 才被拒。

## 十五、抢占实现与验收证据（feat/gesture-preempt）

§十四 的三态方案已按原口径落地（未改设计，只补了一处实现层的坑，见下）。

### 实现（`src/client/`）

- `model.ts`
  - `MotionSource = "idle" | "script" | "gesture"`；`playingSource` 由**唯一入口** `startMotion()` 写入，**只在成功起播时写**。
    这一条是必须的：库在 `priority < 3 && priority <= max(currentPriority, reservePriority)` 时拒绝请求，
    而待机调度会周期性地在被占用的通道上请求 IDLE——若"被拒"也写标记，标记会被改写成 `idle`，
    紧接着的滑动就掉回"没有可抢对象"的静默丢弃。即"记录**在播**动作的来源"，不是"记录**请求过**的来源"。
  - `startGesture()` 承载三态分流（抢占 / 剧本拒绝 / 放弃），**tap 与 flick 共用**：两者都是 NORMAL 的动作缘起输入，
    没有理由"滑动能抢、点击不能抢"（否则一次点击起的动作会把随后的滑动送进死区，反之亦然）。
  - 抢占用 `internal.motionManager.stopAllMotions()`（= `_stopAllMotions()` + `state.reset()` + `stopSpeaking()`）后立刻重试。
    其中的 `stopSpeaking()` 在本插件里是 no-op：口型走参数通道（`model.ts:7` 的注释即此约定），不使用库的 `speak()/lipsync`。
  - 计数器 + 诊断契约：`lvPreemptGesture` / `lvRejectScript` / `lvRejectCooldown` / `lvRejectInvalidGesture`
    （挂载时即发布 0，destroy 一并清理）。按原因分开计数，是为了让"谁拒的"可被观测而不是靠推断。
  - 顺手删除 `playRandomMotion()`：全仓无调用方，且是唯一绕过唯一入口的动作起播路径（留着会让"每次起播都经过 `startMotion`"这句注释失真）。
- `hud.tsx` + `styles.ts`：`touchRefusedFlash` → `.lv-btn.lv-refused` 的 `lv-refused-flash` **200ms** 动画（只闪、不加文字、不弹提示）。
- `view.tsx`：`flashTouchRefused()`（200ms 后复位，重复触发就重计时）接到两个 `mountModel` 调用点。
- README 的触摸模式段与"点击互动"段同步改成新语义（旧文案"静默忽略/点击只在空闲时生效"已不成立）。

### 两个"为错误的机制而绿"的坑（本轮由红转绿，留档）

1. **旧 T5 一直在为死区而绿**。旧写法用 `swipeOnce` + 两次 `page.evaluate` 往返来卡 400ms 冷却窗口，
   实际第二次滑动落在窗口**之后**（~500ms）；它当时"仍被拒"是因为动作还在播（即将被抢的死区），
   与冷却无关——旧注释里"二者观测相同、无法分离"说的就是这个。修复后同一次输入会被抢占并起播，
   于是 T5 直接变红（`preempt 0→1`、`cooldown 0→0`），暴露了真实身份。
   现在两次滑动改为**页内连发**（`swipePairInPage`，用页面自己的时钟卡窗口），T5/T22 同时盯住"值仍为 null"与"计数落在冷却那一格"。
2. **幅度探针第一版把采样点放在 `beforeModelUpdate`，负对照无法判红**。那里读到的参数已被库自带
